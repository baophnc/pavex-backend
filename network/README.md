# Pavex Network Service

Patch 01 establishes regions, hubs, service areas, coverage resolution and the
public hub directory. Patch 02 adds the transport graph and time-aware route
planning.

## Domain decisions

- `parentHubId` models organizational ownership only. It never constrains a
  transport path.
- Regions are database records, not a hard-coded province-to-region enum map.
- A service area points to one primary operational hub and may own many
  province/ward coverages.
- Ward coverage overrides province coverage during resolution.
- Only active hubs explicitly marked `publicVisible=true` appear publicly.
- A `HubLane` is a directed transport edge between any two different hubs.
  Hub hierarchy is not consulted when creating or planning lanes.
- A new lane starts `INACTIVE`. At least one active current/future schedule and
  two active endpoint hubs are required before it can be activated.
- A lane can have many weekly schedules, including several departure times on
  the same day.
- Route planning minimizes actual arrival time (waiting + transfer buffer +
  transit), not merely the sum of transit minutes.
- Vietnam time (`Asia/Ho_Chi_Minh`) is used to resolve recurring departures.
- Each recurring lane schedule owns a per-departure `capacityKg`. Capacity is
  allocated independently for each concrete service date.
- Route planning is capacity-aware: full departures are skipped and the
  planner searches later departures, another preferred template, or the graph
  fallback according to the selected planning mode.
- Capacity reservations are idempotent by `(shipmentId, routeRevision)` and
  transition per leg through `RESERVED -> CONSUMED` or `RESERVED -> RELEASED`.

## Route templates (patch 03)

Route templates replace the old branch-route concept with an explicit operator preference layered on top of the transport graph.

- Templates are created inactive and contain an ordered, contiguous, cycle-free list of hub lanes.
- Activating a template requires every lane, hub, and at least one current/future schedule per lane to be operational.
- Active templates are evaluated by ascending priority; the first template that can produce a scheduled journey is used.
- Routing defaults to `PREFER_TEMPLATE` and falls back to the earliest-arrival graph planner when no template is currently usable.
- Admins can use `GRAPH_ONLY` or `TEMPLATE_ONLY` on the route-plan endpoint for diagnostics.
- Updating a template increments its business `revision`; route-plan responses record the template id, code and revision used.
- `GET /api/v1/admin/network/route-templates/journey` previews the highest-priority currently usable template directly between two hubs.
- Inactive templates can be deleted; active templates must be deactivated first so audit history and operational intent stay explicit.


## Departure capacity and reservations (patch 04)

A schedule now requires `capacityKg`; this is the capacity of each concrete
departure generated by that recurring schedule. Existing schedules are
backfilled to `1000 kg` by Flyway V4 so development data remains usable.

Capacity endpoints:

- `GET /api/v1/admin/network/lanes/{laneId}/capacity?serviceDate=YYYY-MM-DD`
- `GET /api/v1/admin/network/capacity/reservations/{shipmentId}/revisions/{routeRevision}`
- `POST /api/v1/admin/network/capacity/reservations`
- `POST /api/v1/admin/network/capacity/reservations/{shipmentId}/revisions/{routeRevision}/release`
- `POST /api/v1/admin/network/capacity/reservations/{shipmentId}/revisions/{routeRevision}/legs/{legSequence}/consume`

Reservation writes use PostgreSQL transaction advisory locks for the shipment
revision and selected departures. After the locks are acquired, remaining
capacity is checked again before any reservation rows are inserted. If a
departure filled up between planning and reservation, that departure is
excluded and the route is planned again. `NETWORK_CAPACITY_RESERVATION_RETRIES`
controls the bounded retry count (default `8`).

`RESERVED` and `CONSUMED` rows count against capacity. `RELEASED` rows do not.
A partially travelled route may therefore consume completed legs and release
the still-reserved future legs.

Operational safeguards:

- A schedule cannot be deactivated or have its operating window changed while
  it has future `RESERVED` capacity.
- Schedule capacity cannot be reduced below already allocated capacity.
- A lane cannot be changed/deactivated while it has future reserved capacity.
- Raising a lane's maximum shipment weight requires every schedule to have at
  least that much departure capacity.

## Local demo geography seed

The local profile can seed a realistic three-region operating geography for UI and routing development without changing production defaults.

```bash
SPRING_PROFILES_ACTIVE=local ./mvnw -pl network -am spring-boot:run
```

Alternatively enable only the seed explicitly:

```bash
NETWORK_DEMO_SEED_ENABLED=true ./mvnw -pl network -am spring-boot:run
```

The seed is idempotent and preserves active operator-created coverage when a ward is already mapped. It creates three regional gateways, 37 operating service areas with local hubs, and explicit coverage for all 388 commune-level units in the Partners demo scope: Hà Nội (126), Đà Nẵng (94), and Hồ Chí Minh (168). Hub names are plain geographic names; routing identity is carried by hub codes.

After startup, verify the database with:

```bash
./scripts/smoke-network-demo-geography.sh
```

## Demo transport operations seed

With `network.seed.demo.enabled=true`, the geography seed is followed by an operational transport seed. It creates a deterministic, restart-safe demo network for the 37 local operating areas created by the geography seed:

- 74 two-way feeder ROAD lanes between every local hub and its regional gateway;
- 12 inter-gateway trunk lanes: AIR and ROAD in both directions for Hà Nội, Đà Nẵng and Hồ Chí Minh;
- 252 active recurring schedules with per-departure capacity;
- 18 active route templates: EXPRESS, STANDARD and ECONOMY for every ordered metro pair.

The seed intentionally leaves capacity reservations empty. Reservations should be created by Shipment integration or the capacity API so the Capacity UI reflects real reservation lifecycle behavior.

Run `./scripts/smoke-network-demo-transport.sh` after starting the local profile to verify the seeded graph, schedules and route templates.
